Interactive Single-Pass Logit Calculator d1_triage/engine.py

In d1_triage/engine.py, the model does not generate multi-sentence text. Instead, it extracts the final-token logits for positive tokens ("yes", "Yes", "true", "True", "1") and negative tokens ("no", "No", "false", "False", "0"), takes the maximum of each group, and applies a 2-class softmax:

pos_logit = max(logits[pos_ids])
neg_logit = max(logits[neg_ids])
P(TP) = exp(pos_logit) / (exp(pos_logit) + exp(neg_logit))
confidence_pct = |P(TP) - 0.5| * 200

Lesson 06 • Rigorous Evaluation Protocol & Mathematical Formulations

Why Global AUC Lies—and How L0/L2/L3, Within-Rule AUC, P@90R & Rule-Swap Controls Work

Every figure below is verified directly against barryallen16/d1-3B-java-vuln-triage and audit/evaluate_d1.py across 174 real-world Java findings (68 GHSA advisories) and 126 Vul4J repositories.

Gate Level L0 Noisy Location Proxy

L0: File/Method Location Proxy

A Semgrep alert is labeled positive if it merely lands in a file or region touched by a security patch, regardless of whether the Semgrep rule's CWE matches the advisory's CWE. High label noise; favors models that guess based on broad file/rule heuristics.

Gate Level L2 Stored + CWE Match

L2: Stored Hunk + CWE Alignment

Requires both spatial overlap with the vulnerability region AND semantic alignment between the Semgrep rule's CWE family and the GitHub Security Advisory (GHSA) CWE. Filters out coincidental lint alerts on patched files.

Gate Level L3 (Gold Standard) Verified Fix Hunk + CWE

L3: Clean Verified Fix Hunk + CWE

Strictest ground truth (892e47d): the flagged line sits directly inside a verified human-adjudicated security patch diff hunk AND matches the exact CWE of the CVE/GHSA. Zero-shot d1-3B achieves 0.8372 Global AUC and Contrastive LoRA achieves 0.6594 Within-Rule AUC.

The 60-Second Executive Interview Pitch for TriageMate

"TriageMate is a local static-analysis (SAST) alert triage engine for Java that filters out Semgrep false positives in 12 to 14 milliseconds per alert on a single T4 GPU using 6.25 GiB of VRAM.

When I started the project, I followed the standard academic playbook: I parsed Java methods with javalang ASTs and fine-tuned a 4-bit QLoRA Qwen2.5-Coder-7B model on synthetic Juliet and MegaVul datasets, hitting 97.9% accuracy. However, when I audited the predictions, I discovered two critical flaws: first, Juliet had lexical identifier leaks (method names like goodG2B and bad), and second, models trained on synthetic benchmarks suffered complete domain collapse when evaluated on real-world GitHub Security Advisories (GHSA) and Vul4J repositories.

Even worse, when I separated Global ROC-AUC from Within-Rule ROC-AUC across 174 real GHSA alerts and 126 Vul4J repositories, I found that zero-shot models had a high global AUC (0.8372 on L3) simply by memorizing which Semgrep rule IDs were noisy, while their within-rule AUC was 0.4297—worse than a coin flip—because of a line-number disconnect: the model didn't know which statement in the 60-line code window triggered the alert.

I solved this in three steps:
1. Single-Pass Logit Scoring (LiquidAI/d1-3B Hybrid SSM): Instead of slow multi-line autoregressive generation, I extracted single-pass next-token logits over Yes/No exploitability criteria, cutting latency to 12–14 ms.
2. Statement-Level Sink Grounding (d1_triage/sink_finder.py): I built a rule-aware regex sink locator that injects >>> [ALERT LINE n] directly on the vulnerable sink line. Without changing a single model weight, L0 Within-Rule AUC jumped from 0.4297 to 0.5986 (and L2 to 0.6321).
3. Real-to-Real Contrastive LoRA & Rule-Swap Controls: By fine-tuning on 416 real pre-patch vs. post-patch commit pairs, L3 Within-Rule AUC reached 0.6594 (+14.94% over Kev-4B), and paired rule-swap controls proved a strictly positive code signal delta (+0.0749 on L0, +0.1106 on L3), proving the model actually inspects Java dataflow rather than guessing from rule names."
