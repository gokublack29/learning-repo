Lesson 0008

Fast Inference and Lossless Byte Fallback

How encoder.rs turns new text into token IDs in microseconds, merges by rank priority, and handles unseen characters without data loss.

Step 8 of 13. The algorithm. What happens at encode time, and why nothing is dropped.

1. The Runtime Inference Pipeline

When you call encoder.encode(text), the text flows through three distinct steps in encoder.rs:

1
Chunking (pretokenizer.rs)

Splits text into independent words and punctuation boundaries using the Unicode regex we explored in Lesson 4.

2
Character Seeding

Converts each chunk into a sequence of starting character symbols.

3
Priority Merging (apply_merges)

Scans neighbor pairs and repeatedly merges the pair with the lowest rank until no more merges apply.

4
Byte Fallback

Any character or byte not in the subword vocabulary is emitted as a raw byte token (<0xNN>). Nothing is ever dropped.

2. Why Merge Priority (Rank Order) Matters

During training, the most frequent pairs are learned first. The order in which merges are learned is called their rank:

  • Rank 0: The #1 most common pair in the training corpus (highest priority).
  • Rank 100: Less common than Rank 0.
  • Rank 29,999: Learned near the very end of training.

At inference time, if a word contains multiple candidate pairs, the encoder always merges the lowest rank pair first. This guarantees that tokenization is 100% deterministic and matches exactly how the model was trained.

3. Systems Engineering: CSR Layout Merge Table

How does the encoder look up whether two adjacent token IDs (a, b) have a merge rule?

The Hash Map Cache Disaster

In early versions, the merge table was a standard HashMap<(u32, u32), (u32, u32)>. At 120,000 merges, the hash map became so large that it blew past the CPU's L1/L2/L3 hardware caches.

Every lookup caused a CPU cache miss, plummeting throughput from 17.4 MB/s down to 7.3 MB/s.

In encoder.rs:72-84, the author replaced the hash map with a Compressed Sparse Row (CSR) layout:

  • starts: Vec<u64>: A tiny bitset. With 1 bit per token ID, it checks in 1 CPU instruction: "Does token A start any merge rule at all?" If 0, it skips instantly without touching RAM.
  • data: Vec<u64>: A contiguous array packing second token b, rank, and new_id into a single 64-bit integer. Lookups stay inside fast CPU cache lines.

4. The Lossless Guarantee: Byte Fallback (Never <unk>)

What happens when a user types text with an unseen character, an emoji (🔥), or a rare foreign symbol?

Traditional tokenizers throw an unknown token error and replace the text with <unk>, losing the information forever.

This tokenizer uses byte fallback: every byte from 0 to 255 has its own dedicated token (<0x00> to <0xFF>). Look at what happens to the fire emoji in our real test:

Input: "தமிழ் 🔥"

Tokens without specials: [374, 428, 516, 607, 31585, 31504, 31493, 31510]

Notice the last 4 tokens: the 4 UTF-8 bytes of 🔥 (0xF0 0x9F 0x94 0xA5) are mapped into byte tokens. When decoded, it reconstructs "தமிழ் 🔥" with zero data loss.
