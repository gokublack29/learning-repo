Lesson 0007

The BPE Training Engine and 64-bit Pair Packing

How trainer.rs processes millions of words, counts neighbor pairs at hardware speed, and exports tokenizer JSON files.

Step 7 of 13. The algorithm. The training loop and the pair packing.

1. The BPE Training Loop: Step by Step

Training a tokenizer is an iterative greedy search. Given a corpus file and a target merge count (e.g. 50,000), trainer.rs executes four phases:

1
Parallel Word Counting (Rayon)

Instead of looping through gigabytes of text character-by-character, Rayon distributes lines across CPU threads to count unique words and their frequencies. If the word "தமிழ்நாடு" appears 5,000 times, it is stored once with a counter of 5,000.

2
Initial Base Token Seeding

Every unique word is split into its starting base tokens (the 1,135 seed tokens from vocab.rs, including consonants, vowels, and conjunct stems).

3
Adjacent Pair Counting

For every word, count every neighbor pair. In a word with tokens [A, B, C], the pairs are (A, B) and (B, C). Each pair's score is multiplied by the word's corpus frequency.

4
Merge and Repeat

Pick the pair with the highest overall frequency. Mint a new token ID for it, record the merge rule (left, right) -> new_id, replace that pair inside all affected words, and repeat for the next iteration.

2. Three Systems Engineering Tricks in trainer.rs

A naive BPE trainer written in Python can take hours or days to run 50,000 merges. This Rust codebase finishes in minutes because of three specific systems decisions:

Trick A: 64-bit Bit-Packed Pair Keys

In standard code, a token pair is stored as a tuple of strings or structs: ("வண", "க்கம்"). Allocating millions of tiny string objects creates severe memory fragmentation.

Look at trainer.rs:16-23:

#[inline]
fn pack_pair(a: TokId, b: TokId) -> u64 {
    ((a as u64) << 32) | (b as u64)
}

How bit-packing works:

A token ID is a 32-bit integer (u32). A 64-bit integer (u64) has 64 bits of space. By shifting token a 32 bits to the left and placing token b in the lower 32 bits, the entire pair fits into a single CPU register with zero heap allocations.

Trick B: Max-Heap (BinaryHeap) for O(1) Lookups

If you have 100,000 active candidate pairs, scanning all 100,000 pairs to find the most frequent pair at every merge step would be terribly slow (O(N) per merge). The trainer uses a BinaryHeap (priority queue): the top of the heap always presents the highest-frequency pair in O(1) time.

Trick C: Inverted Index (pair_positions)

When pair (A, B) merges into C, how does the engine know which words to update? Scanning all unique words in the corpus would waste enormous time.

Instead, pair_positions: HashMap<u64, HashSet<usize>> maintains a list of exact word indices containing that pair. The trainer only touches the words that actually contain the pair.

3. The Output Artifact: tamil_tokenizer.json

When training finishes, trainer.save_tokenizer_with_reserved_tokens writes a JSON file containing three sections:

  1. "vocab": A map from every token string to its integer ID ({"<|startoftext|>": 987, "வணக்கம்": 974...}).
  2. "merges": An ordered list of pairs ([["ண", "்"], ["ட", "ி"], ...]). The order of this list is strictly preserved because inference must apply earlier merges first!
  3. "metadata": Total vocabulary size, merge count, and training duration.
