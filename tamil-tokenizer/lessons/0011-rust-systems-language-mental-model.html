1. What makes Rust a systems language

You have written Python or JavaScript. Both languages hide the machine behind a runtime that owns your memory, checks your types at runtime, and throws exceptions when things go wrong. Rust removes all three layers. The trade is that the compiler now insists on knowing who owns what.

Concern Python / JavaScript Rust (this repo)
Memory freeing Garbage collector, pauses at unpredictable times Deterministic, at the end of the owner's scope
Type errors Found while the program is running Found while the program is compiling
Failure handling Exceptions, thrown from anywhere, caught anywhere A value in the return type, the compiler forces a branch
Deployment Needs the runtime installed One static binary, no runtime
Speed Interpreted, object overhead per value C-like, but with the memory bugs prevented

What Rust gives up: no inheritance, no null, no exceptions, no free-form pointers without a fight with the compiler. What it gives back: a tokenizer that processes 122,000 merges at 17 MB/s without a garbage collector ever running, which is exactly the goal of encoder.rs.

2. Stack and heap

Every value lives in one of two places, and the difference decides how fast your code runs.

STACK                              HEAP
+---------------------------+        +----------------------------+
| text:  &str              |  ptr -> | "வணக்கம்" as UTF-8 bytes   |
| len:   15                 | -------+ | 15 bytes, owned by String  |
+---------------------------+        +----------------------------+
| id:    974                |          (allocated, then freed)
+---------------------------+
Lives on the stack Lives on the heap
u32, u64, usize, bool, char, Option<T>, Result<T, E>, tuples and arrays of those, a struct of those (for example Symbol) String, Vec<T>, HashMap, Box<T>, Arc<T>, anything behind a reference whose size is not known at compile time

The stack is a fixed region the function pointer moves through. Push and pop are a pointer bump, measured in nanoseconds. The heap is a large arena the program asks the allocator for chunks of. Every heap allocation costs a call to the allocator, and freeing costs another.

This is why Vec<u32> is fast and Vec<Vec<u32>> is slower even when both hold the same numbers. The outer Vec is one allocation holding 32-bit integers back to back. The inner one is a pointer per element, and every read is a cache miss chasing that pointer.

Where this shows up in the repo

encoder.rs keeps id_to_token: Arc<Vec<String>>. The Vec is one contiguous heap block, so decoding token 9000 is one array index, not a hash lookup. The Arc around it is a reference counter so the map can be shared with other structures without copying 122,000 strings.

3. Ownership: one value, one owner

Every value in Rust has exactly one owner. When the owner goes out of scope, the value is dropped and its memory is freed. There is no free() to call and no garbage collector to wait for.

fn main() {
    let name = String::from("வணக்கம்");   // owner: `name`
    {
        let borrowed = &name;             // a read-only view, owner is still `name`
        println!("{}", borrowed);
    }                                     // `borrowed` view ends, `name` still owns the bytes
    println!("{}", name);                // still valid
}                                         // `name` drops here, bytes are freed

The compiler tracks this. If you pass a String into a function and the function stores it somewhere that outlives the caller's scope, the compiler rejects the program. That is the whole idea of Rust in one sentence: memory errors become compile errors.

Here is the rule in practice, from trainer.rs:

let merged = format!("{}{}", token1, token2);   // `merged` owns a fresh String

self.token_to_id.insert(merged.clone(), new_id);  // the map takes ownership, so it needs a copy
self.id_to_token.push(merged.clone());            // the Vec takes ownership, so it needs another copy
self.merges.push((token1.clone(), token2.clone()));

Those .clone() calls are not optional. insert and push both take the value by ownership, and merged is used again in the log line further down. The clone copies the bytes onto the heap, so you pay for it. Rust never hides a copy: every copy is written down.

The habit to build

When you read Rust, look for .clone(), .to_string(), and .to_owned(). Each one is a heap copy the programmer asked for on purpose. In a performance-focused file like encoder.rs, a .clone() inside a loop is a bug waiting to happen.

4. Move, Copy, Clone

When ownership transfers, the original variable becomes unusable. This is called a move.

let a = String::from("தமிழ்");
let b = a;          // ownership moved into `b`
// println!("{}", a);  // compile error: `a` was moved

The bytes are not copied. Only the pointer, length, and capacity move, and the old binding is marked dead. The compiler then refuses to let you use a, which is what stops a double free.

Small, plain-data types opt out with Copy. Copying them is a bitwise copy and the original stays usable.

#[derive(Clone, Copy, Debug)]
struct Symbol {
    start: usize,
    end: usize,
    id: Option<u32>,
}

This is from encoder.rs. Symbol is 24 bytes of plain numbers, so copying it is free and the compiler allows it. Look at how it is used:

for sym in &symbols {          // & means iterate by reference, no copy
    if let Some(id) = sym.id {  // Option<u32> is Copy, so `id` is a plain copy
        token_ids.push(id);
    }
}
Trait Meaning Cost
Copy Bitwise copy on assignment, original stays valid Free, the value is small and has no destructor
Clone Explicit deep copy you call yourself Real work, a heap allocation for a String
neither Ownership moves, original is dead Free, a pointer copy

5. Borrowing: the one rule

Moving is expensive when you do not need it, so Rust lets you borrow instead.

  • &T is a shared borrow. Many readers allowed at once, nobody may change the value.
  • &mut T is an exclusive borrow. One writer, and no readers while it is alive.

In one line: at any moment you may have many shared borrows or one mutable borrow, never both.

On a method, &self means "this method reads the struct", and &mut self means "this method changes the struct".

impl FastBPEEncoder {
    // Reads the encoder. Many threads can call this at the same time.
    pub fn encode(&self, text: &str) -> Vec<u32> { ... }

    // Changes the encoder. Nobody else may touch it during the call.
    fn merge_pass(&self, symbols: &mut Vec<Symbol>, ...) { ... }
}

Here is the payoff for a tokenizer. encode_batch hands the same encoder to every core at once:

pub fn encode_batch<T: AsRef<str> + Sync>(&self, texts: &[T]) -> Vec<Vec<u32>> {
    use rayon::prelude::*;
    texts.par_iter().map(|t| self.encode(t.as_ref())).collect()
}

The compiler checks this for you. self is borrowed immutably by every thread, so the encoder's fields must not be mutated while encoding runs. That is why the merge tables and the vocab are immutable after FastBPEEncoder::build returns.

When the borrow checker complains, it is usually pointing at a real design problem: two pieces of code want the same data at the same time. The fixes are always one of three: copy the data, split the borrow so the two pieces touch different fields, or restructure so the phases do not overlap.

6. Lifetimes: the tie between input and output

A lifetime annotation says how long a borrowed value must stay alive. It does not change how long anything lives, it just states the rule so the compiler can check it.

// pretokenizer.rs
pub fn pretokenize<'a>(&self, text: &'a str) -> Vec<&'a str> {
    self.pattern.find_iter(text).map(|m| m.as_str()).collect()
}

Read it out loud: "the slices I return point into text, so text must outlive every slice I hand back."

The 'a appears three times and all three must be the same lifetime. It is written explicitly here because the output borrows from the argument rather than from self, and the compiler cannot guess which one you meant.

In practice you write lifetimes rarely. The compiler infers them when there is one obvious answer:

pub fn merges(&self) -> &[(String, String)] { &self.merges }
// The output borrows from self, so it cannot outlive the trainer.
The 90 percent rule

You will see &'a str in this repo maybe a dozen times. Everywhere else, the lifetimes are invisible. Do not go looking for them. If you ever need to name one, it will be because the compiler told you to.

7. How the data structures actually sit in memory

Each container in this repo is a deliberate choice about memory layout.

Type Layout Used here for
Vec<T> One heap block: pointer, length, capacity. Elements back to back. id_to_token, offsets, data, token IDs
String A Vec<u8> that is guaranteed valid UTF-8. Every token's text, the corpus lines
HashMap Buckets of key and value pairs, hashed at runtime. Order is not preserved. token_to_id, pair_freq
FxHashMap Same shape, but the hash is a cheap integer mix. Not resistant to hostile input. The encoder's vocab and special tokens
AHashMap Hash map with a per-process random seed. The trainer's pair counters
BinaryHeap An array arranged so the largest element sits at index 0. The trainer's priority queue of pairs
Arc<T> A pointer plus an atomic reference count. Sharing the vocab across threads

Two details worth internalizing. First, a HashMap gives no order guarantee, which is why vocab.rs sorts by ID before writing JSON, and why lib.rs rejects a vocab whose IDs have gaps. Second, Vec::remove shifts every later element left, so it costs O(n). encoder.rs calls it inside the merge loop, which is the hot path and the reason the chunk cache matters.

8. Bit packing: the first real systems trick

Look at how the trainer keys its pair counters:

type TokId = u32;

#[inline]
fn pack_pair(a: TokId, b: TokId) -> u64 {
    ((a as u64) << 32) | (b as u64)
}

#[inline]
fn unpack_pair(p: u64) -> (TokId, TokId) {
    ((p >> 32) as TokId, (p & 0xFFFF_FFFF) as TokId)
}
bit 63        32 31         0
    +-------------+-------------+
    |  token a    |  token b    |
    |  (u32)      |  (u32)      |
    +-------------+-------------+

Why bother, when a (u32, u32) tuple would work? Two reasons, both about the machine.

  1. Memory. A tuple of two u32 is 8 bytes but it is not a single scalar value, so a hash map key of that type usually points at heap-allocated key storage. A u64 is one scalar, hashed with a couple of multiply and shift instructions.
  2. Speed. Hashing an integer is one multiply. Hashing a tuple means hashing two integers and combining them, every single lookup. The trainer does millions of lookups per merge.

The encoder pushes this further and packs three values into one word:

#[inline]
fn pack(b: u32, rank: u32, new_id: u32) -> u64 {
    (b as u64) | ((rank as u64) << 21) | ((new_id as u64) << 42)
}

#[inline]
fn unpack_b(entry: u64) -> u32 { (entry & 0x1F_FFFF) as u32 }
#[inline]
fn unpack_rank(entry: u64) -> u32 { ((entry >> 21) & 0x1F_FFFF) as u32 }
#[inline]
fn unpack_new_id(entry: u64) -> u32 { ((entry >> 42) & 0x1F_FFFF) as u32 }
bit 63     42 41      21 20       0
    +----------+----------+----------+
    | new_id   |  rank    |    b     |
    | 21 bits  | 21 bits  | 21 bits  |
    +----------+----------+----------+

21 bits holds up to 2,097,151. That is enough for a token ID, a merge rank, and a replacement ID at a 120K merge budget, so all three fit in one 64-bit word with one bit to spare. One cache line fetch now returns the whole rule.

Read the numbers, not the comment

The comment above the merge table says "17 bits each". The mask 0x1F_FFFF is 21 bits, and the shifts are 21 apart, so the fields are 21 bits each. The code is right and the comment is wrong. This is the normal state of code: trust the arithmetic.

You will meet this idiom constantly in systems Rust. #[inline] tells the compiler the function is small and hot, so it inlines the body instead of making a call. as u64 is a numeric cast, checked at compile time here because the types are fixed width.

9. CSR layout: trading a hash lookup for a slice

The obvious way to store merge rules is a hash map from (a, b) to a rule. This repo deliberately does not do that. The MergeTable in encoder.rs stores them in compressed sparse row form.

offsets:  [ 0 ][ 1 ][ 2 ][ 3 ] ... [ vocab_size ]
            |      |      |      |             |
            |      |      |      |             +-- end of row for token 3
            |      |      |      +---------------- start of row for token 3
            |      |      +----------------------- start of row for token 2
            |      +------------------------------ start of row for token 1
            +------------------------------------- start of row for token 0

data:     [ rules for token 0 ][ rules for token 1 ][ rules for token 2 ] ...

lookup(a=2, b=7):
    slice = data[offsets[2] .. offsets[3]]     // usually 0 to 3 entries
    scan the slice for b == 7

The trick is that each token is the result of at most one merge, so the pairs starting with a given token are few. Sort all pairs by their first token, and the rules for token a end up contiguous. A lookup becomes one sequential read of a short slice plus a couple of comparisons.

There is a second guard. Most adjacent pairs in a chunk have no rule at all, and the starts field is a bitset with one bit per token ID:

starts: Vec<u64>   // one bit per token ID, set if that ID starts a merge

fn starts_with(&self, a: u32) -> bool {
    self.starts[(a / 64) as usize] & (1u64 << (a % 64)) != 0
}

That single bit test answers "is there any rule starting here" without touching the two large arrays. It is the reason the hot loop stays fast even though the table is bigger than the CPU cache.

The comment in the source records the measurement: a hash map at 120K merges cost 2.4 times the throughput, 17.4 down to 7.3 MB/s, because the table stops fitting in cache and every probe misses. The CSR layout cost 17 percent. Same data, different memory layout, different speed. That is the kind of decision a systems language exists to make possible.

10. Traits: Rust's polymorphism

Rust has no classes and no inheritance. A trait is a promise about what a type can do, and any type can implement any trait. Polymorphism happens through traits instead of through a base class.

Trait The promise In this repo
Copy, Clone Can be copied, either free or deep Symbol, HeapEntry, WordData
Debug Can be printed with println!("{:?}", x) Nearly every struct
Default Has a sensible empty value TamilPretokenizer, special token config
Display Has a human readable form, {} TokenizerError
Error Is an error type that can be reported TokenizerError
From, Into Can be converted from another type Error conversions for the ? operator
Ord, PartialOrd, Eq Has a total order, so it can go in a sorted container HeapEntry in the priority queue
Serialize, Deserialize Can be written to and read from JSON TokenizerData, written by serde_json
Send, Sync Safe to move to other threads, or share across them Required by rayon for par_iter

The hand-written ordering

Most traits are derived, which means the compiler writes the implementation:

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct HeapEntry {
    key: u64,
    count: u32,
}

The derived PartialEq compares both fields. The ordering cannot be derived, because the tie-break is a deliberate choice, so it is written by hand:

impl Ord for HeapEntry {
    fn cmp(&self, other: &Self) -> Ordering {
        match self.count.cmp(&other.count) {
            Ordering::Equal => other.key.cmp(&self.key), // Reversed like HuggingFace
            other => other,
        }
    }
}

Work out what that does. BinaryHeap is a max-heap, so the element it considers greatest pops first. The trainer wants the most frequent pair first, so a higher count must compare as greater. That is the first line. On a tie, the trainer wants the smaller packed key to win, so other.key.cmp(&self.key) is reversed: a smaller key compares as greater, so it pops first.

This hand-written comparison is why training is deterministic. Two runs on the same corpus produce the same model, byte for byte. The comment in trainer.rs about sorting before assigning IDs exists for the same reason.

Trait defaults

impl Default for TamilPretokenizer {
    fn default() -> Self {
        Self::new()
    }
}

This lets any type that implements Default be created with TamilPretokenizer::default(), which is what generic code expects. It is the standard Rust way to say "a sensible empty value exists".

11. Generics and monomorphization

Generic types and functions are written with angle brackets:

Vec<u32>          // a vector of u32
HashMap<String, u32>  // string to id
Option<T>            // maybe a T
Result<T, E>          // either a T or an E
pub type TrainedTokenizer = (FxHashMap<String, u32>, Vec<(String, String)>);

Unlike a class-based language, Rust does not erase generics at runtime. It generates a separate copy of the code for each concrete type used. Vec<u32> and Vec<String> compile to two different machine code functions with no type check inside. This is called monomorphization, and it is why generics in Rust are fast.

Generic functions can require capabilities of the type parameter:

pub fn encode_batch<T: AsRef<str> + Sync>(&self, texts: &[T]) -> Vec<Vec<u32>> {
    use rayon::prelude::*;
    texts.par_iter().map(|t| self.encode(t.as_ref())).collect()
}
  • T: AsRef<str> means the type can be viewed as text. The same function accepts &str, String, or &String without any conversion code.
  • T: Sync means the type is safe to share across threads. Rayon requires it, so the compiler asks for it here.
  • texts: &[T] is a borrowed slice, so no copy of the input collection is made.

Note that the bound is written on the function, not on the struct. FastBPEEncoder is not generic at all. Generic functions over concrete types is the common Rust pattern.

12. Errors are values

There are no exceptions in Rust. A function that can fail returns a Result, and the compiler forces the caller to deal with it.

pub enum TokenizerError {
    Io(std::io::Error),
    Json(serde_json::Error),
    InvalidData(String),
}

pub type Result<T> = std::result::Result<T, TokenizerError>;

An enum is a tagged union. The value is one variant, plus enough space for the largest variant's payload. TokenizerError holds an I/O error, a JSON error, or a message. That is why it can be matched exhaustively:

impl std::fmt::Display for TokenizerError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            Self::Io(e) => write!(f, "I/O error: {}", e),
            Self::Json(e) => write!(f, "JSON error: {}", e),
            Self::InvalidData(msg) => write!(f, "Invalid data: {}", msg),
        }
    }
}

impl std::error::Error for TokenizerError {}

impl From<std::io::Error> for TokenizerError {
    fn from(e: std::io::Error) -> Self { Self::Io(e) }
}

impl From<serde_json::Error> for TokenizerError {
    fn from(e: serde_json::Error) -> Self { Self::Json(e) }
}

The From implementations are what make the ? operator work across different error types. The whole chain, from lib.rs:

fn parse_id(path: &str, token: &str, value: &serde_json::Value) -> TokenizerResult<u32> {
    let id = value.as_u64().ok_or_else(|| {
        TokenizerError::InvalidData(format!("{}: id for {:?} is not an integer", path, token))
    })?;
    u32::try_from(id).map_err(|_| {
        TokenizerError::InvalidData(format!("{}: id for {:?} is out of range", path, token))
    })
}

Line by line:

  • as_u64() returns Option<u64>. ok_or_else turns the None into an error, and the ? unwraps the Ok or returns early with the error.
  • u32::try_from(id) returns Result<u32, TryFromIntError>. The ? here converts that error into TokenizerError using the From impl above. Without that impl the ? would not compile.
  • map_err replaces the error with a better message but keeps the same error type.
  • The function returns Result<u32, TokenizerError>, so the caller must handle the failure.

And this is what the caller does in encode.rs:

let (vocab, merges) = match load_tokenizer(vocab_file) {
    Ok(v) => v,
    Err(e) => {
        eprintln!("Failed to load vocab: {}", e);
        std::process::exit(1);
    }
};
Why this matters more than exceptions

With exceptions, a function that can fail does not say so in its signature, and a caller can forget to handle it. With Result, the failure path is part of the type, and the compiler lists every call site that has not dealt with it. In a 1,135 token vocab loaded from a file, that is the difference between a crash at 3am and a message at startup.

13. Iterators and closures

An iterator is a value that describes a sequence of values, possibly lazily. Chaining them reads like a pipeline.

self.pattern.find_iter(text).map(|m| m.as_str()).collect()
         |                  |                    |
         |                  |                    +-- gather into a Vec<&str>
         |                  +----------------------- transform each match into its text
         +------------------------------------------ every match of the pattern

The |m| m.as_str() part is a closure: an anonymous function that captures what it needs from the enclosing scope. Here it captures nothing, so it compiles to a plain function pointer with no overhead.

The common adapters you will see:

Adapter What it does Here
.iter() Iterate over borrowed items for sym in &symbols
.map(f) Transform each item .map(|t| self.encode(t.as_ref()))
.filter(p) Keep only the items that pass a test .filter(|k| k.starts_with("<|reserved_"))
.collect() Gather into a collection texts.par_iter().map(...).collect()
.fold(a, f) Accumulate into one value Counter updates in the trainer
.par_iter() Same, split across all cores Corpus loading and batch encoding

Iterators in Rust are not slower than a hand-written loop. The compiler turns the chain into the same machine code, which is the meaning of zero-cost abstractions. Write them in whichever style reads better.

14. Threads, Arc, and Send/Sync

Rust's thread model is compile-time checked. Two traits carry the whole idea.

Trait Meaning
Send This value can be moved to another thread
Sync This value can be shared by reference across threads

Most plain data types are both. A type containing a raw pointer or a lock is neither, and the compiler will stop you from sharing it. The fix is usually to wrap it in a Mutex or an Arc.

Arc is an atomic reference count. Cloning an Arc is cheap and safe from any thread. This is how the encoder shares its vocab:

pub struct FastBPEEncoder {
    token_to_id: Arc<FxHashMap<String, u32>>,
    id_to_token: Arc<Vec<String>>,
    merges: MergeTable,
    promotions: MergeTable,
    pretokenizer: TamilPretokenizer,
    special_tokens: FxHashMap<String, u32>,
    ...
}

Every field is immutable after build returns. That is what lets encode_batch call self.encode() from every core at once without a lock.

Rayon is the library that makes this easy. It runs a fixed thread pool and splits the work automatically:

// trainer.rs, corpus loading
let chunk_size = all_lines.len() / rayon::current_num_threads().max(1);
let chunk_size = chunk_size.max(50000);

let partial_results: Vec<HashMap<Vec<String>, u32>> = all_lines
    .par_chunks(chunk_size)
    .map(|chunk| {
        let pretok = TamilPretokenizer::new();
        let mut local_freqs = HashMap::new();
        for line in chunk {
            let chunks = pretok.pretokenize(line);
            for chunk_text in &chunks {
                let tokens = self.segment_into_clusters(chunk_text);
                *local_freqs.entry(tokens).or_insert(0) += 1;
            }
        }
        local_freqs
    })
    .collect();

Read it as: split the lines into chunks, process each chunk on its own thread, each thread keeps a private counter map, then merge the maps. Rayon steals work from busy threads when others go idle, so an uneven split still uses every core.

One line is worth flagging: let pretok = TamilPretokenizer::new(); sits inside the closure on purpose. Each thread builds its own regex, so there is no shared mutable state and no lock.

15. Zero-cost abstractions and the build flags

"Zero cost" means an abstraction you use in source costs nothing extra in the binary. Rust's iterators, generics, and traits are all zero cost: they are resolved at compile time into plain machine code.

The build flags in Cargo.toml are the other half of the story:

[profile.release]
opt-level = 3      // full optimization
lto = true          // link-time optimization: let the linker see across crates

opt-level = 3 is the usual maximum optimization level. lto = true lets the compiler optimize across crate boundaries, which matters here because regex, serde_json, and the tokenizer crate all end up in one binary.

Inside the source, #[inline] marks the small hot functions so the compiler inlines them instead of making a call. pack, unpack_b, unpack_rank, unpack_new_id, starts_with, and get in encoder.rs are all marked, because they sit inside the innermost loop.

Debug versus release

cargo run builds unoptimized, which can be 10 to 30 times slower. Every number in the README was measured with --release. If you benchmark without it, you are measuring the compiler's lack of effort.

16. A checklist for reading any Rust file

When you open an unfamiliar Rust file, work through these in order. It takes two minutes and saves an hour of confusion.

1
Read the imports

use lines tell you the vocabulary. A renamed import such as use ahash::{AHashMap as HashMap, AHashSet as HashSet}; means the rest of the file says HashMap but means a specific one.

2
Find the structs

Each struct is a memory layout. Ask what is on the stack and what is on the heap.

3
Find the impl blocks

impl Foo holds the methods. impl Trait for Foo holds behaviour the type did not write itself, like ordering or serialization.

4
Read every signature

&self reads, &mut self writes, Result can fail, Option can be absent, &T borrows. The signature is the contract.

5
Find the ? and match

These are the error paths. They usually sit at the edges of a function, and they tell you what the function considers recoverable.

6
Spot the copies

.clone(), .to_string(), format!. Each one is a heap allocation. In a hot loop, that is the thing to fix.

7
Ask what the compiler promised

If it compiles, the borrows do not overlap, the types match, and every error path is handled. You do not need to check those yourself.

17. Worked example: annotate encode_inner

This is the whole model applied to the function that does the actual work. It is about 25 lines.

fn encode_inner(&self, text: &str) -> Vec<u32> {
    let mut token_ids = Vec::with_capacity(text.len() / 3);
    let chunks = self.pretokenizer.pretokenize(text);

    let mut symbols = Vec::with_capacity(64);
    let mut cache: Vec<Option<(u32, u32)>> = Vec::with_capacity(64);
    for chunk in chunks {
        symbols.clear();
        self.seed_chars(chunk, &mut symbols);
        self.apply_merges(&mut symbols, &mut cache);
        for sym in &symbols {
            if let Some(id) = sym.id {
                token_ids.push(id);
            } else {
                self.push_text(&mut token_ids, &chunk[sym.start..sym.end]);
            }
        }
    }

    token_ids
}
Line What the compiler guarantees What happens at runtime
fn encode_inner(&self, text: &str) The encoder is borrowed read-only, the text is borrowed read-only. Neither is copied. Nothing
Vec::with_capacity(text.len() / 3) One heap block, sized up front so push never reallocates. One allocation of about a third the input size
pretokenize(text) The returned &str slices cannot outlive text. The lifetime says so. The regex engine scans the string and collects slice pointers
symbols, cache Scratch buffers, allocated once and reused for every chunk. No allocation per chunk
seed_chars(chunk, &mut symbols) Exclusive borrow of symbols for the call only. One Symbol per character, with its byte range
apply_merges(&mut symbols, &mut cache) Two different variables, so two mutable borrows coexist. The same variable twice would be rejected. Repeatedly merges the lowest ranked pair until no rule applies
for sym in &symbols Shared borrow of symbols while token_ids is separately borrowed. Disjoint, so it compiles. One token ID per symbol
if let Some(id) = sym.id Option<u32> has no null. Either a known token ID, or a character the vocab does not hold. Push the ID, or fall back to one token per UTF-8 byte
&chunk[sym.start..sym.end] The byte range is checked against the string boundaries, so this cannot panic on a bad index. A slice, no copy

Now the same function from a systems point of view. The pretokenizer allocates a vector of slices. Each merge shrinks the symbol vector with Vec::remove, which shifts memory. The rule cache is a parallel array that is invalidated at exactly the two positions next to a merge. The token IDs are pushed into a vector that was sized for them at the start. The whole thing touches memory in a predictable, linear pattern, which is why it runs at tens of megabytes per second.
