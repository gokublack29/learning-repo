Lesson 0012

The canonical model and the Hugging Face export

Two engines, six commits of disagreement, one shared model, and the export that writes five files.

Step 12 of 13. Shipping. How two engines became one tokenizer.

1. The problem: two models, two tokenizations

You have a Rust encoder and a Python export. Both read the same trained JSON file. For six commits they disagreed on the token IDs for about a fifth of all lines.

The cause was not a bug. It was architecture. Each side built its own model from the same file:

THE RUST ENCODER                        THE HF EXPORT
-------------------------                -------------------------
seed a chunk with the                    add 256 byte tokens
longest base cluster                     add promotion merges
(1,135 clusters)                         append missing characters
merge ONE occurrence                     merge EVERY occurrence
per pass                                per pass

RESULT: the same text, different token IDs.

Three attempts to fix it in the export alone, and what each one measured:

Attempt Measured ID agreement
Keep HF's ByteLevel pretokenizer 0%. It byte-maps the text before BPE sees it, so no raw-text merge in the file can ever match
Register the base clusters as added_tokens 0%. HF extracts added tokens before the BPE model runs, so the model never fires and output collapses to characters
Make the export reproduce the pretokenizer and the base clusters 71.8% on wiki, 73.0% on IndicCorp. It stalled there
Fix the encoder, share one model between both sides 100%, and the token count difference went to 0.0%

HF's BPE model has no seed-symbol concept. It always starts from single characters. So the encoder could not keep its greedy longest-match seeding and still be equivalent to the export. The encoder was the side that was wrong.

What the fix actually was

Delete the Aho-Corasick base automaton from the encoder. Seed one symbol per character, the way HF does. Merge every occurrence of the best-ranked pair in one pass, the way HF does. Then put both sides on one canonical_model() that builds the vocabulary, the byte tokens and the promotion merges, so there is only one model and one merge list in the repo.

2. The canonical model

model.rs is 166 lines and does four things. Everything else in the export reads its output.

canonical_model(vocab, merges) -> CanonicalModel

1. append the characters a token uses but the vocab lacks   (added_prims)
2. append the 256 byte tokens, spelled <0x00> .. <0xFF>
3. build the promotion merges                                (promotions)
4. return vocab + promotions ++ learned merges

Step 1: the characters the vocab is missing

A token like க்ஷ uses three characters. If the vocabulary does not hold one of them as its own token, then that character cannot be looked up, so the input cannot be represented. The model finds every such character and appends it as a new token with the next free ID.

let mut missing: Vec<char> = vocab
    .keys()
    .flat_map(|t| t.chars())
    .filter(|c| !vocab.contains_key(&c.to_string()) && !byte_chars.contains(c))
    .collect();
missing.sort_unstable();
missing.dedup();
let added_prims = missing.len();

Sorting matters. The IDs are assigned in sorted order, so the same trained file always produces the same canonical model.

Step 2: the byte tokens

for b in 0..=255u8 {
    vocab.insert(format!("<0x{b:02X}>"), next_id);
    next_id += 1;
}

The spelling is Hugging Face's, because that is what its ByteFallback decoder looks for. Any character not in the vocabulary is emitted as one token per UTF-8 byte, which keeps encoding lossless for any input at all.

3. The promotion merge algorithm

This is the hardest piece of logic in the repo, so walk it slowly.

A promotion merge rebuilds a multi-character base cluster out of single characters. Without it, a token like க்ஷ is unreachable in HF, because HF can only reach a token through a merge.

Which tokens need one

let produced: HashSet<String> = merges.iter()
    .map(|(a, b)| format!("{a}{b}")).collect();

let mut reachable: HashSet<String> = byte_chars.iter()
    .map(|c| c.to_string())
    .chain(vocab.keys().filter(|t| t.chars().count() == 1).cloned())
    .collect();

let mut candidates: Vec<&String> = vocab.keys()
    .filter(|t| t.chars().count() > 1
             && !produced.contains(*t)
             && !reachable.contains(*t))
    .collect();
  • produced: tokens a learned merge already creates. No promotion needed.
  • reachable: single-character tokens plus the byte table characters. These need zero merges.
  • candidates: everything else, multi-character and unreachable.

Order matters: longest token first

candidates.sort_by_key(|t| (std::cmp::Reverse(t.chars().count()), (*t).clone()));

A promotion's rank decides which merge happens when several are available, and the encoder resolves overlaps by longest match. Emitting the four-character token before the three-character ones is what makes the reconstruction build the longer token instead of stopping at the shorter one.

The second key, the token text itself, makes the sort total. A HashMap iterates in a random order, so without it the same file would produce different promotions on different runs.

The recursive split

fn split(token: &str, vocab, reachable) -> Option<Vec<(String, String)>> {
    if reachable.contains(token) {
        return Some(Vec::new());
    }
    let chars: Vec<char> = token.chars().collect();
    for k in (1..chars.len()).rev() {
        let left: String = chars[..k].iter().collect();
        let right: String = chars[k..].iter().collect();
        if !vocab.contains_key(&left) || !vocab.contains_key(&right) {
            continue;
        }
        let (Some(a), Some(b)) = (
            split(&left, vocab, reachable),
            split(&right, vocab, reachable),
        ) else {
            continue;
        };
        let mut out = a;
        out.extend(b);
        out.push((left, right));
        return Some(out);
    }
    None
}

Read it as: find a split point where both halves are themselves vocabulary tokens, split each half the same way, and emit the inner rules first.

Two rejected approaches are documented in the code comments, and they are the two mistakes you would make yourself:

// A flat greedy pass would take the whole token as one part and emit nothing.
// A plain prefix pass cannot build ஸ்ரீ, since ஸ்ர is not a token while ஸ்ர and ரீ both are.

Work ஸ்ரீ through the real algorithm, three characters: ஸ, ், ரீ.

1
Try the longest prefix first

k = 2: left is ஸ்ர, which is not a token. Skip.

2
Try the shortest prefix

k = 1: left is ஸ, a Grantha consonant, so it is a token. Right is ்ரீ, a consonant plus vowel sign, so it is a token too. Both sides are in the vocabulary.

3
Recurse into the right side

்ரீ is not reachable on its own, so split it again. k = 1: left ்ர is a single consonant, reachable. Right ீ is the vowel sign, which was appended in step 1 of the canonical model, so it is reachable too. The rule is ர + ீ.

4
Emit inner rules first

The rules come back as (ர, ரீ) then (ஸ, ரீ). The inner rule has to run first, otherwise ரீ does not exist yet when the outer rule needs it. That ordering is why the function returns a list and not a single pair.

How many promotion merges

819 for any model built on the current 1,135-token base vocab, at both 30K and 120K merges. You can check it yourself: cargo run --release --bin export_hf -- output/v5_mixed_120000_prefixed.json out prints 120819 merges (819 promotions). The small sample model in the repo prints 291, because its vocabulary predates the current byte table and has far fewer multi-character clusters to rebuild.

Where the promotions sit

let promotions = build_promotions(&vocab, merges, &byte_chars);
let mut all_merges = promotions.clone();
all_merges.extend(merges.iter().cloned());

CanonicalModel {
    vocab,
    merges: all_merges,
    promotions: promotions.len(),
    added_prims,
}

Promotions come first in the list, so their ranks are lower than any learned merge. A base cluster therefore exists before any learned merge that consumes it. The encoder keeps the two lists in separate tables anyway, because there are only a few hundred promotions and they run against single characters, so the whole table fits in cache while the learned merges do not.

4. The export

export_hf.rs writes five files. The Rust side of the export is now a thin wrapper over canonical_model().

File Who reads it
tokenizer.json The Hugging Face tokenizers library. The main artifact.
tokenizer_config.json transformers. Holds model_max_length and the special token names.
special_tokens_map.json transformers. Written alongside the config so the two cannot drift.
vocab.json The slow tokenizer. A flat token to ID map.
merges.txt The slow tokenizer. Rank order, one pair per line.

The pre-tokenizer

"pre_tokenizer": {
    "type": "Sequence",
    "pretokenizers": [
        {
            "type": "Split",
            "pattern": { "Regex": pattern },
            "behavior": "Isolated",
            "invert": false,
        },
    ],
},

The pattern is our own Tamil-aware regex, pulled straight from the pretokenizer so the two engines cannot disagree about it.

The decoder, and the trap inside it

let decoders = vec![json!({ "type": "ByteFallback" })];

ByteFallback alone. Never ByteLevel after it.

The earlier version was a sequence of ByteFallback then ByteLevel, and it silently corrupted Latin-1 text. ByteFallback assembles <0xNN> into bytes and returns a UTF-8 string. ByteLevel then re-applies the GPT-2 table to that output, so a decoded é, which is itself a GPT-2 stand-in for byte 0xE9, got turned back into the raw byte and then decoded to U+FFFD.

Measured: across 3,988 Latin-1-bearing lines in four corpora, 2,074 decoded corrupted before the fix and none did after. Decode fidelity on the sample corpus went from 95.7% to 100%.

Two config traps

  • model_max_length goes in tokenizer_config.json, never in tokenizer.json. HF's tokenizer.json schema rejects the field, and writing it there makes the file unloadable. The default is now u64::MAX, because a published tokenizer should not silently truncate a caller's input.
  • eos_token is the empty string, because the empty string is a real token in this vocabulary. An empty string in the config resolves to no token, so tok.eos_token used to come back None even though the token was there.

5. The gates

A tokenizer that corrupts text, or will not load, is worse than no tokenizer. scripts/publish_hf.py refuses to upload on any of these:

Gate Threshold
Decode fidelity on every held-out split 100.0%
ID agreement against the Rust encoder 99.0% floor. Not 100, because anything below that is a bug in one of the two engines
Install check AutoTokenizer loads from the repo root and from a subfolder, bos, eos, pad and unk all resolve, Tamil and Latin-1 round-trip
Prove it yourself
cargo run --release --bin export_hf -- output/v5_mixed_120000_prefixed.json output/_check
cargo build --release --bin encode_lines
.venv/Scripts/python.exe scripts/verify_hf_export.py \
  output/v5_mixed_120000_prefixed.json output/_check data/tamil_wiki_clean.txt 500

Expect ids match 500 (100.0%) and decode ok 500 (100.0%). Two independent engines, one vocabulary, one merge list, identical output.

6. What to say if it comes up in an interview

The short version: the two engines disagreed on a fifth of lines and the cause was that each built its own model. I tried to fix the export three times and got to 79 percent. The fix was to admit the encoder was the side that was wrong, because HF's BPE has no seed symbols and always starts from characters. I deleted the encoder's base automaton, made both sides seed per character and merge every occurrence per pass, and put both on one shared canonical model. The remaining piece was the promotion merges, which rebuild each base cluster out of characters so that a character-seeded BPE can reach it at all. Now both engines agree on 100 percent of inputs, and the publish script refuses to upload an artifact that disagrees.
